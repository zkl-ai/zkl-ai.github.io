# 第 1 章：从一段代码到引擎骨架

先放一段能跑的最简代码：

```python
from vllm import LLM, SamplingParams

prompts = ["你好，请用一句话介绍你自己", "写一个把列表倒序的 Python 函数"]
sampling_params = SamplingParams(temperature=0.8, top_p=0.95)

llm = LLM(model="Qwen/Qwen3.5-0.8B")
outputs = llm.generate(prompts, sampling_params)
```

用 0.8B 的小模型，纯粹是为了下载快、单卡能跑，方便反复改参数看现象。要观察的机制跟模型大小没关系。

## 这两行代码管的不是一回事

我一开始把 `LLM(...)` 和 `generate(...)` 当成一件事，读源码才发现它们管的东西完全不同。

`LLM(...)` 构造的时候在"准备"：读权重、跑一次假前向量一下显存、据此决定 KV cache 能开多少 block、把 decode 阶段的算子录成 CUDA Graph。这些决定了这台机器**最多能同时服务多少个请求**。

`generate(...)` 的时候在"跑"：请求进队列，引擎一步步循环——每步挑一批请求、跑一次前向、把新 token 拼回去。这些决定了**每条请求要多久**。

所以后面第 2 章讲构造，第 3 章讲生成，是两条独立的线。

## 引擎的分层

顺着源码往下读，层次是这样的。下面的缩进就是嵌套关系，右边是「文件:行号」：

```
LLM                               entrypoints/llm.py:67
└── LLMEngine                      v1/engine/llm_engine.py:48
    ├── renderer                   :91
    ├── input_processor            :94
    ├── output_processor           :97
    └── engine_core ──────────►    :109   EngineCoreClient
        └── EngineCore             v1/engine/core.py:105
            ├── model_executor     :134
            ├── structured_output_manager  :146
            └── scheduler          :162   → v1/core/sched/scheduler.py:79
                └── kv_cache_manager       scheduler.py:299
                    └── KVCacheManager     v1/core/kv_cache_manager.py:134
```

有两处我读的时候停顿了一下。

一处是 `LLMEngine` 和 `EngineCore` 中间隔着一个 `EngineCoreClient`（`llm_engine.py:109`）。它看着像多余的一层，其实是部署方式的适配层：单进程跑的时候它就是直连，多进程跑的时候它负责跨进程传消息，而 `LLMEngine` 不用改。

另一处是 `kv_cache_manager` 的位置。我第一次画图时把它和 `model_executor`、`scheduler` 画成了三个并列的框，后来翻到 `scheduler.py:299` 才发现它是在 `Scheduler.__init__` 里创建的，是 Scheduler 的成员。它为什么在调度器里，第 4 章讲调度时会说清楚——简单说，能不能接纳一个请求，取决于显存够不够，这是调度决策的直接输入。

## 请求的状态机

一条请求从进来到结束会走一个状态机。0.30.0 的定义在 `v1/request.py:364`，一共 12 个状态。

主干是 `WAITING → RUNNING → FINISHED_*`，中间可能被 `PREEMPTED` 打断，之后再回到 `RUNNING`。围绕主干长出来的，是几个高级特性带来的状态：`WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR`（等引导解码的文法编译完）、`WAITING_FOR_REMOTE_KVS`（等远端 KV，P/D 分离场景）、`WAITING_FOR_STREAMING_REQ`。结束状态有 6 种，区分不同的终止原因，比如正常停止、超过长度、被主动中止、出错。

这里有个细节我挺喜欢：源码把所有 `FINISHED_*` 的枚举值都排在 `PREEMPTED` 之后，于是判断请求是否结束就一行——`status > PREEMPTED`（`request.py:386`）。用枚举的先后顺序来表达"是否结束"，省掉了一个专门的状态字段。

顺带说下，0.30.0 比 Anatomy 那篇博客（基于 2025 年 8 月的 commit）多了不少东西：`renderer` 是新增的组件，状态机从 3 个粗粒度状态细化到 12 个，KV 管理里也多了一层 `coordinator`（`kv_cache_manager.py:170`）。博客没写错，只是框架在往"支持更复杂模型结构"的方向走。

## 两张要画的图

这一章建议画两张图，后面几章还会反复用。

**图 1.1，引擎分层。** 就照上面那段缩进画成嵌套方框：最外是 `LLM`，往里是 `LLMEngine`（里面并排放 `renderer`、`input_processor`、`output_processor`），然后是 `EngineCoreClient`，再往里是 `EngineCore`（里面放 `ModelExecutor`、`StructuredOutputManager`、`Scheduler`），最里面在 `Scheduler` 框内再套一个 `KVCacheManager`。每个框右下角标上「类名 + 文件:行号」，这样图本身就是一份源码索引。画的时候注意别把 `KVCacheManager` 画成和 `Scheduler` 并列——上面踩过这个坑。

**图 1.2，请求状态机。** 主线 `WAITING → RUNNING → FINISHED_*`，从 `RUNNING` 引一条回环到 `PREEMPTED` 再回来。`WAITING` 旁边挂那三个分支状态，六个结束状态画成一簇。可以在 `PREEMPTED` 旁边标一句"它之后的枚举值都算结束"。

## 动手做

光看源码很容易"以为懂了"。下面几步建议真的做一遍：

1. 把上面那段代码跑起来，模型几百 MB，很快。
2. 构造完 `LLM` 之后打印一下对象，看看层次对不对：
   ```python
   type(llm.llm_engine)
   type(llm.llm_engine.engine_core)
   ```
   如果属性名对不上，就去 `entrypoints/llm.py` 里搜 `self.llm_engine`，看它到底挂在哪。"找不到就翻源码"这个动作本身也是在练。
3. 打开 `v1/engine/core.py`，翻到 105、134、146、162 行，确认 `EngineCore` 里确实是这三样东西。
4. 打开 `v1/request.py`，把 12 个状态数一遍，找到 386 行的 `is_finished`。

## 自测

1. `LLMEngine` 和 `EngineCore` 各管什么？为什么要拆成两层？
2. "构造决定容量、生成决定速度"——这两件事在源码里分别对应哪些方法？
3. `EngineCoreClient` 是干什么的？如果去掉它会怎样？
4. 为什么 `status > PREEMPTED` 能判断一个请求结束？

想不出来可以先回看，再往下走。

（参考答案：第 1 题，前者管输入输出格式、后者管执行循环，拆开是为了让格式和执行解耦；第 2 题，构造阶段对应 `determine_available_memory` 和 `initialize_from_config`，生成阶段对应 `EngineCore.step` 里的调度；第 3 题，它是单进程直连和多进程通信的统一抽象；第 4 题，因为所有结束状态在枚举里都排在 `PREEMPTED` 后面。）

下一章钻进 `LLM(...)` 的构造函数，看 `init_device` → `load_model` → `determine_available_memory` → `initialize_from_config` 这条链，重点是 KV cache 能开多少 block 是怎么算出来的。
